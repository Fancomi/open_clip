## 1. 问题

gemma4 重写的 dense 长 caption（平均 132 BPE token）拿来直接训 CLIP，
长文本检索很强但**短文本能力报废**：`gemma_dense` COCO i2t 7.70% / IN-1k **0.96%**
（全量口径；随机基线 0.10%，即只剩 10× 随机）。
反过来只用 gt 短文（`gt_base`）短文本正常但长文本只有 18.30%。

Long-CLIP (ECCV 2024) 的 **PCM（Primary Component Matching）** 声称能兼顾两者：
主分支用长文本对齐完整图像特征，短分支用**PCA 降维后**的图像特征对齐短 caption。
降维迫使短文本只匹配图像的"主要语义"，从而在长文本主导训练时保住短模板 zero-shot。

本页回答三个问题：
1. PCM 在我们的基座（projective SigLIP + VISReg，非原论文的 standard CLIP）上是否有效？
2. `pcm_weight` / `pcm_dim` 怎么取？
3. 长短能力的 trade-off 是真实存在的，还是超参没调好？

## 2. 实现

| 组件 | 位置 |
|---|---|
| PCA 降维（含三级兜底） | `src/open_clip/model.py:CLIPLeJEPA._pca_reduce` |
| 双分支前向（`text` 长 / `text2` 短） | `src/open_clip/model.py:CLIPLeJEPA.forward` |
| `pcm_loss` 累加（复用主损失，含 neg_mode） | `src/open_clip/loss.py:1501` |
| CLI: `--pcm-weight` / `--pcm-dim` / `--csv-caption2-key` | `src/open_clip_train/params.py:593` |
| 启动入口 | `scripts/train/visreg.sh pcm`（`PCM_WEIGHT` / `PCM_DIM` 可覆盖） |
| 数据 | `clip_train_dual.tsv`（`filepath` / `caption_short` / `caption_dense`） |

短分支损失：`pcm_weight × SigLIP(PCA_k(img_feat), txt_short_feat)`，
`PCA_k` = 保留前 k 个主成分后重建回原空间（不改变维度，只降秩）。

**与原论文的三处差异**（都是被基座逼出来的，不是随意改动）：

1. **口径**：原论文是 standard CLIP（`cos → +1`）；我们主线是 projective（`|cos| → 1`）。
   两个口径各跑一组作对照（`pcm_proj` / `pcm_std`），见第 4 节。
2. **PCA 数值稳健性**：`torch.linalg.svd` 在训练后期 embedding 条件数变差时会抛
   `_LinAlgError: failed to converge (512)` —— `pcm_dim=64` 组实测 epoch 5 崩。
   现在是三级兜底：jitter 重试 → `pca_lowrank` → 退化为全维对齐（不中断训练）。
   见 commit `c31b5bc`。
3. **文本塔 batch-max 截断**：短分支 caption 实测最多 34 token，固定跑 256 窗口
   纯属浪费。按 batch 内 EOT 最大位置截断，数值等价（差异 1e-7），
   PCM 训练整体加速 ~1.7×。见 `model.py:_trim_to_batch_max` / commit `a4338fc`。

## 4. 结论

### 4.1 PCM 有效，但原论文的 `pcm_weight=1.0` 是错的取值

以 `gt_base`（同 epoch、同口径、无长文本）为对照，Δ 后标注 2σ 判定（判据见 §5.8）。
**IN-1k 与 k-NN 两列均为 2026-08-25 全量口径重测值（各 50000 图），
2σ 同步更新为 0.32 / 0.30**：

| | COCO i2t | COCO t2i | IN-1k（全量） | Urban i2t | k-NN bb（全量） |
|---|---|---|---|---|---|
| gt_base（绝对值） | 23.14% | 16.35% | 23.27% | 18.30% | 44.73% |
| 2σ 判据 | 0.75 | 0.13 | 0.32 | ~~1.92~~ **2.36** | **0.30** |
| **pcm_w0.2**（最优） | **+5.46** ✅ | **+0.98** ✅ | **−1.74** ✅ | **+41.20** ✅ | **−3.29** ✅ |
| pcm_w0.1 | **+5.24** ✅ | **+0.77** ✅ | **−2.39** ✅ | **+42.50** ✅ | **−4.34** ✅ |
| pcm_w0.3 | +3.08 ✅ | −0.08 ❌ | **−2.16** ✅ | +39.40 ✅ | **−4.24** ✅ |
| pcm_proj (w1.0，原论文) | −1.06 ✅ | −1.62 ✅ | **−3.07** ✅ | +29.00 ✅ | **−5.26** ✅ |

`pcm_w0.2` **在短文本检索的两个方向和长文本上同时显著超过 gt_base**：
COCO i2t **+5.46**、COCO t2i **+0.98**、Urban i2t **+41.20**。

⚠️ **2026-08-25 修订（两轮）**：
1. IN-1k 那一列原先写的是 −0.20 ❌「落在噪声内，无代价」，那是 2000 图子集口径的假象。
   全量重测后是 **−1.74，超 2σ 五倍以上，显著为负**。
2. k-NN 那一列原先写的是 −0.80（勉强越界，"量级很小"）。
   `eval_knn_probe.py` 用的是同一批 100 个 wnid，同样偏置。
   全量重测后是 **−3.29，11 倍 2σ** —— 不是"很小"。

**PCM 不是"免费"的，代价有两笔**：用 IN-1k 短模板分类的 **−1.74** 和
图像塔 k-NN 的 **−3.29**，换来 Urban 长文本的 **+41.20** 与 COCO i2t 的 **+5.46**。
这个交换在图文检索的目标下仍然划算，但**如果目标里包含"拿到一个更好的图像 backbone"，
PCM 是净亏的** —— 详见 §5.3 与 §7 的重判。
PCM 全系在 IN-1k 与 k-NN 上都为负，且大体随 w 增大而恶化（k-NN 的例外见 §5.3：峰在 w=0.2）。

注意 t2i 这一项的演进：`w=0.3` 时是 −0.08（噪声内，说不清），
到 `w=0.2` 变成 **+0.98 显著为正** —— 短文本检索的**两个方向都真实变强了**，
不再是"i2t 涨、t2i 持平"的单边提升。

### 4.2 `pcm_weight` 完整曲线：最优区间 [0.1, 0.2]，已探到底

五个取值全部跑完（d=32 固定，全部 epoch_10；IN-1k 与 k-NN 均为全量口径）：

| w | COCO i2t | COCO t2i | IN-1k（全量） | Urban i2t | k-NN bb（全量） |
|---|---|---|---|---|---|
| **0.1** | 28.38% | 17.12% | 20.88% | **60.80%** | 40.39% |
| **0.2** | **28.60%** | **17.33%** | **21.53%** | 59.50% | **41.44%** |
| 0.3 | 26.22% | 16.27% | 21.11% | 57.70% | 40.49% |
| 0.5 | 25.70% | 15.90% | 21.20% | 56.10% | 40.31% |
| 1.0（原论文） | 22.08% | 14.73% | 20.20% | 47.30% | 39.47% |

⚠️ k-NN 列已换成全量口径。旧子集值（0.1=44.35 / 0.2=45.00 / 0.3=45.25 / 0.5=43.95 /
1.0=42.30）给出的是"w 越小图像特征越差"的单调下降，**方向是错的**：
全量口径下 **w=0.2 是 k-NN 的峰值**，比 0.1 高 1.05（3.5σ）、比 0.3 高 0.95（3.2σ）。
**这让 w=0.2 从"四口径里三个最优"升级为"五个口径里四个最优"**（只有 Urban i2t 输给 0.1 且在噪声内）。

相邻取值逐对 2σ 判定（判据见 §5.8；左减右）：

| 对比 | COCO i2t | COCO t2i | IN-1k（全量） | Urban i2t |
|---|---|---|---|---|
| **0.1 vs 0.2** | **−0.22 ❌** | −0.21 ✅ | **−0.65 ✅** | **+1.30 ❌** |
| 0.2 vs 0.3 | **+2.38 ✅** | +1.06 ✅ | +0.42 ✅ | +1.80 ❌ |
| 0.3 vs 0.5 | +0.52 ❌ | +0.37 ✅ | −0.09 ❌ | +1.60 ❌ |
| 0.5 vs 1.0 | **+3.62 ✅** | +1.17 ✅ | **+1.00 ✅** | **+8.80 ✅** |

**结论**：

1. **0.1 与 0.2 在短/长文本检索上不可分辨**，但**全量 IN-1k 把它们分开了**：
   0.2 比 0.1 高 0.65 点（超 2σ=0.32 两倍）。旧子集口径下这一项是 +0.10 ❌，
   看不出差别。**因此"工程取 0.2"现在有了直接证据，不再只是并列首选中的任选一个。**
   曲线仍已到平台，不必再往 0.1 以下扫。
2. **0.2 显著优于 0.3**（COCO i2t +2.38）→ 拐点落在 0.2 ~ 0.3 之间。
3. **最优区间是 w ∈ [0.1, 0.2]**，工程上取 **0.2**（COCO 两轴最好、Urban 与 0.1 无显著差异）。
4. 原论文的 **w=1.0 是明确的坏取值**，在两个轴上都被 w≤0.5 显著超越。

⚠️ 一个未解释的现象：**COCO t2i 的每一对相邻比较都显著**（含 0.1 vs 0.2 的 −0.21），
因为它的 2σ 只有 0.13（全口径最小）。这意味着 t2i 对 w 的响应比其他口径更敏锐 ——
但 0.1 与 0.2 在 t2i 上的方向（0.2 更好）与 Urban 上的方向（0.1 更好）相反，
所以 [0.1, 0.2] 内部谁更优取决于你更看重哪个轴，不存在全局最优。

机制推测：短分支的 PCA 秩约束（32/1024）本身是对完整 embedding 的强扭曲，
w=1.0 时它与主分支正面冲突；w 小的时候它退化成一个**正则项** ——
足够引导短模板能力，又不足以破坏表示。曲线在 0.2 以下走平，
说明再降权重已经不改变"正则项"这个角色。

### 4.3 `pcm_dim` 影响远小于 weight，且非单调

| d（w=1.0 固定） | COCO i2t | IN-1k（全量） | Urban i2t |
|---|---|---|---|
| 16 | 22.64% | 18.54% | 50.20% |
| 32（原论文） | 22.08% | 20.20% | 47.30% |
| 64 | 24.54% | 21.44% | 47.90% |

按 §5.8 的 2σ 判据，这几个差异**多数是显著的**（与我此前"不足以排序"的说法相反）：

| 对比 | Δ | 2σ | 判定 |
|---|---|---|---|
| d64 vs d32（COCO i2t） | +2.46 | 0.75 | ✅ 显著 |
| d16 vs d32（Urban i2t） | +2.90 | ~~1.92~~ **2.36** | ⚠️ **1.23× → 未决**（旧判 1.5× 显著） |
| d16 vs d32（IN-1k 全量） | −1.66 | 0.32 | ✅ 显著 |
| d64 vs d32（IN-1k 全量） | +1.24 | 0.32 | ✅ 显著（子集口径下是 +0.30，看不出来） |
| d64 vs d32（Urban i2t） | +0.60 | **2.36** | ❌ 噪声内（0.25×，不变） |

所以 dim 确实有影响，且**非单调**：d=32（原论文值）在 COCO 上最差、
~~d=16 长文本更好~~但 IN-1k 掉 1.66、d=64 短文本最好、IN-1k 也最好（+1.24）但长文本无差异。
⚠️ **08-27 地板实标后，"d=16 长文本更好"退役为未决**（+2.90 只有 1.23× 地板）。
→ **dim 这个旋钮上，长文本一列已经没有任何可判的差异**（+2.90 与 +0.60 都是未决/噪声），
可判的只剩 COCO i2t 与 IN-1k 两列。选 dim 时不要再用长文本当理由。
全量口径下 IN-1k 随 dim 单调递增（18.54 → 20.20 → 21.44），
这与"降维越狠、短模板语义丢得越多"的机制解释一致 —— 子集口径掩盖了这条趋势。

**但这一整组的前提有问题**：dim 扫描全部在 `w=1.0` 下做，而 §4.2 已证明
`w=1.0` 是坏取值。**最优 w 附近的 dim 行为完全未知**，这组数字不能外推。

### 4.4 PCM 的短分支还**提升**了长文本能力

`pcm_w0.1` Urban i2t **60.80%** > `gemma_dense`（100% dense，无短分支）**51.60%**，
差 **+9.20**（**3.9× 新地板 2.36**，显著；旧地板 1.92 下是 4.8×，结论不变）。

**纯长文本训练并不是长文本能力的上限** —— 加一个轻量短分支（w=0.1）反而让长文本
更强。短分支同时起到正则作用。这一点原论文未提及（原论文的短分支定位是
"保住 zero-shot"，是防守性的）。

`pcm_w0.2` 的 59.50% 同样显著超过纯 dense（+7.90）。

### 4.5 PCM 优于朴素混合与拼接

同为"让模型见到 dense"的三种做法：

| 做法 | COCO i2t | Urban i2t |
|---|---|---|
| **PCM（w0.2）** | **28.60%** | **59.50%** |
| mix50（50% 行整体替换） | 21.06% | 46.10% |
| concat（每行 gt+dense 拼接） | 训练即崩 | — |

PCM 赢 mix50：COCO **+7.54**、Urban **+13.40**（两轴都远超 2σ）。
concat 直接崩（IN-1k 0.50%，2000 图子集口径，未重测），推测是拼接后文本分布与两个来源都不一致，
等于给了个第三种畸形分布。

### 4.6 projective 在 PCM 上的优势比在 gt 上更大

| 数据 | proj − std（COCO i2t） | proj − std（IN-1k 全量） | proj − std（Urban i2t） |
|---|---|---|---|
| PCM (w1.0 d32) | **+5.30** | **+1.97** | +1.70 |
| gt only | +1.32 | −0.07 | +1.60 |

口径本身的收益（gt 上 +1.3）到了 PCM 上放大到 +5.3。
**全量重测让这条结论更干净**：gt only 上两口径的 IN-1k 差从 −0.65 变成 −0.07（噪声内，
即"gt 数据上换口径对分类无影响"），而 PCM 上是 +1.97（显著为正）。
未验证的推测：`|cos|` 的射影等价让长短两个分支更容易共存于同一空间。
**注意**：跨口径不可比绝对值，这里比的是「同数据下两口径的差」，是合法的二阶对比。

### 4.7 dense 长文本确有可泛化价值

Urban-1k 与 CC3M / COCO 均零重叠，排除记忆效应：见过 dense 的模型
（pcm 系 / mix50 / gemma_dense）Urban i2t 全部 ≥45%，只见过 gt 短文的
（gt_base 18.30% / gt_std 16.70%）不到 19%。**分界线干净**。

## 5. 纯图像口径：IN-1k k-NN probe

### 5.1 为什么需要它

第 3 节的三个评测**全部把文本当分类器或 query**：COCO 是短句检索、
IN-1k zero-shot 把类名套模板变成文本分类器、Urban-1k 是长文本 query。
所以它们测的都是**图文对齐质量**，无法区分：

- 图像塔学到了更好的视觉特征？
- 还是只是文本塔更会对齐？

k-NN probe 把文本彻底移出链路：冻结骨干 → 提特征 → 近邻投票。
零训练、无可调项（除 k）、DINO 系的标准图像侧指标。

**方法**：IN-1k val **1000 类 × 50 图（50000 样本，全量，随机基线 0.10%）**。
留一法 k-NN（k=20，余弦相似度 + `softmax(sim/0.07)` 加权投票，对角排除自身）。
两个特征层都测：

> ⚠️ **2026-08-25 口径整改**：本节此前用 `100 类 × 20 图 = 2000` 子集。
> `in1k_fullscope_retest.md` 证明这批「前 100 个 wnid」会让 IN-1k zero-shot 的
> **组间排序都翻转**，而 `eval_knn_probe.py:80` 取的是同一批 wnid，同样偏置。
> 已把全量改成默认值并重测 24 个模型（`/tmp/knn_full_retest.log`）。
> 改动前先在旧口径上复现了 `gt_base_0811 = 45.80 / 43.55`，与历史逐位一致，
> 证明重构（DataLoader 多进程 + GPU 分块 k-NN）本身数值等价。
> **本节所有数字均为全量口径，旧的 2000 图数字一律作废。**

| 层 | 取法 | 维度 | 含义 |
|---|---|---|---|
| `backbone` | `visual.trunk.forward_features(x)[:, 0]` | 768 | 投影头**之前**的原始视觉特征 |
| `proj` | `encode_image(x, normalize=True)` | 1024 | 对齐文本空间**之后**的特征 |

入口 `scripts/eval/eval_knn_probe.py`。全部取 `epoch_10.pt`，与第 3 节同 epoch。

`pcm_weight` 这个旋钮的结论因此更硬，而不是更软。**

### 5.4 gemma_dense 的谜团：图像塔和文本塔一起弱

这是本节最有价值的对照。`gemma_dense`（100% dense，无短分支）zero-shot 全量口径只有
**0.96%**（子集口径 1.70%），随机基线 0.10% —— 即只剩 10× 随机；
但此前**无法判断是图像塔坏了还是文本塔坏了**，因为 zero-shot 两者耦合。

k-NN 给出答案：**backbone 32.96%，全场最低，比 `gt_base` 低 11.77 点（39σ）。**

32.96% 仍远高于随机（0.10%，全量 1000 类）—— 约 330× 随机，说明图像塔确实学到了
实质视觉语义，**它没崩**。但它是所有变体里最弱的，而且差距远比子集口径显示的大
（子集：39.85%，−5.95；全量：32.96%，−11.77，被压缩了一半）。
所以「纯 dense 训练失败」是**双重失败**：

- 文本塔崩到不可用（zero-shot 全量 0.96%，只剩 10× 随机）
- 图像塔同时退化 **11.77 点**（不是原先估的 6 点）

**长文本监督对视觉特征学习本身是有害的**，不只是让文本塔偏离短模板分布。
`gemma_dense` 与 `pcm_w0.2` 的对照给出了 PCM 短分支的真正作用：
短分支把图像塔的退化从 −11.77 收回到 −3.29，**挽回了七成**，但没能消除。

| pcm_d16 (w1.0) | −0.69 | 有 PCM 短分支 |
| pcm_w0.5 | −0.40 | 有 PCM 短分支 |
| gemma_dense | −0.11 | 无短分支（100% dense） |
| pcm_d64 (w1.0) | 0.00 | 有 PCM 短分支 |
| **pcm_w0.2** | **−0.06** | 有 PCM 短分支 |
| pcm_w0.3 | **+0.03** | 有 PCM 短分支 |
| pcm_w0.1 | **+0.31** | 有 PCM 短分支 |

**这条旧结论在全量口径下不但成立，而且变得干净得多**：六个 gt 系运行全部落在
−1.42~−1.74 的窄带里，七个 PCM 组全部落在 −0.93~+0.31，**两组完全不重叠**，
间隙 0.49 远超 Δ 的复现散度。子集口径下 gt_base 是 −2.25 单点、PCM 系 −0.20~+0.75 散乱，
现在有了六个对照点，判据从"一次观察"升级为"两个不重叠的分布"。

唯一的例外是 `gemma_dense`（−0.11，无短分支却几乎不掉）—— 但它的 backbone 只有 32.96%，
投影前就已经很差，没什么可丢的，属于地板效应，不构成反例。
`mix50`（−0.99，无短分支但含 dense）落在两组之间，说明**dense 文本本身也有一点保真作用**，
PCM 短分支只是把它做到了极致。

机制上讲得通：PCA 短分支要求**投影后特征的前 k 个主成分仍能对齐短 caption**，
这等于在阻止投影头把视觉判别信息压缩掉。

这个效应此前完全不可见 —— 所有旧评测只看投影后的特征，看不到"投影前后差了多少"。
**这是 PCM 的一个原论文未提及的副作用，且方向是正面的。**

⚠️ 但要与 §5.3 合起来读：PCM 保住的是「投影头不再额外丢信息」，
代价是「投影前的 backbone 本身掉了 3.3 点」。
净效果 —— `pcm_w0.2` 的 proj 41.38 vs `gt_base` 的 proj 43.28，**仍然低 1.90 点（6.6σ）**。
**投影头保真挽回不了 backbone 的损失。**

### 5.6 指标间相关性：优化都发生在文本侧

以 k-NN backbone 为自变量算 Pearson 相关。
**下表为 2026-08-25 全量口径重算**（k-NN、IN-1k 均为 50000 图；
COCO 全 5000 图；Urban 全 1000 图）：

| 样本集 | n | r(COCO i2t) | r(IN-1k zs) | r(Urban i2t) |
|---|---|---|---|---|
| 长文本路线（§5.2 的 10 组） | 10 | +0.776 | **+0.896** | −0.418 |
| 同上，剔除极端点 gemma_dense | 9 | +0.213 | **+0.925** | −0.616 |
| 长文本 + 区域监督全部变体 | 19 | +0.672 | **+0.921** | **−0.821** |

（历史子集口径同一批 10 组：COCO +0.748 / IN-1k +0.802 / Urban −0.398；
剔除 gemma_dense 后 IN-1k +0.704。）

**IN-1k 的正相关在全量口径下大幅增强**（+0.802 → +0.896，剔除极端点后 +0.704 → +0.925）。
剔除极端点后仍有 0.925，说明这不是被 `gemma_dense` 一个点拉出来的：
**图像特征质量几乎单调决定短模板分类能力**。子集的采样噪声此前在稀释这个信号。

**COCO 的正相关反而在剔除极端点后崩掉**（+0.776 → +0.213）。
这是新出现的、与旧口径不同的现象：短句检索比短模板分类更依赖文本塔 ——
`pcm_w0.2`（k-NN 41.44）的 COCO i2t 28.60 比 `gt_base`（k-NN 44.73）的 23.14 高 5.46 点，
图像塔更差却检索更强。**COCO i2t 不能当图像塔质量的代理指标**，IN-1k zero-shot 可以。

**Urban 负相关是关键，且在扩到 19 组后强化到 −0.821**：
长文本能力与图像特征质量**系统性反向** —— 越擅长长文本的模型图像特征越弱。
长文本能力主要由文本塔承担，并且**是用图像塔的质量换来的**。

另一个观察 —— 各口径的全距（长文本路线的原 10 组，即 `gt_base` / `pcm_*` / `mix50` / `gemma_dense`）：

| 口径 | 最好 − 最差 | 旧子集口径 |
|---|---|---|
| k-NN backbone | **11.77 点** | 5.95 点 |
| COCO i2t | 20.90 点 | 同（COCO 一直全 5000 图） |
| IN-1k zero-shot（全量） | 22.31 点 | 同（已是全量） |

**图像塔的组间全距从 5.95 翻到 11.77，翻了一倍。** 旧口径下"图像塔在变体间只差 6 点、
文本侧差 20 点上下"这个对比支撑了"本轮所有优化本质上都在动文本塔"的判断。
全量口径下 11.77 vs 20.90 —— 差距缩小到不足 2 倍，
**图像塔并非"没被动过"，而是被长文本监督实实在在地动坏了。**

图像塔在 8 个变体间只差 6 点，文本侧差 20 点上下。
**本轮所有优化（PCM / mix / concat / 口径）本质上都在动文本塔**，
图像塔的改进空间尚未被触及。

### 5.7 自比评测的四级阶梯

至此形成一套按「文本长度」递进、并带一个零文本基准的自比体系：

| 口径 | 文本参与 | 文本长度 | 测什么 |
|---|---|---|---|
| **IN-1k k-NN** | ❌ 无 | — | 图像特征质量 |

**Urban-1k 方差最大** —— 1000 图、1:1 配对，样本量小，符合预期。
🆕 **2026-08-27 Urban 两行按四运行口径重标**（加入第四次同配方运行 `gt_base_0806`，

⚠️⚠️ **更要紧的一条：n=4 时 σ̂ 自己的 95% CI 是 ×[0.567, 3.73]**，
i2t 的"2σ=2.36"真值可能在 1.34~8.81 之间 →

**Urban 是唯一大量结论卡在 1~2× 的口径。** 详见 [[eval_protocol]] §4.6.1/§4.6.2，
全站连带修订清单见 §4.6.3。
**k-NN 全量最稳（0.30）**，与 IN-1k 全量（0.32）同级 ——
两者都是 5 万样本的分类型指标，样本量把方差压得很低。

COCO i2t 只有 5000 个 query，所以反而是 0.75。

这也是为什么全量化 IN-1k 和 k-NN 之后，一批原本"噪声内"的差异变成了显著项。
🆕 **08-27 加上 DOCCI 后这条规律要打个折**：DOCCI（5000 query）实标 **i2t 2σ=1.47 /

排掉一个混淆：DOCCI 上 `gt_base` 的 p = 14.52%、Urban 是 18.30%，同量级

**换集后一定要报 p，否则说不清是谁的功劳。** 详见 §4.8 与 [[eval_protocol]] §4.6.4。

⚠️ **已知瑕疵**：s1/s2 跑在含 `_trim_to_batch_max`（a4338fc）与 PCA 兜底（c31b5bc）

| COCO i2t / t2i | +5.24 / +3.57 | 96% / 107% |
| DOCCI i2t / t2i | +5.96 / +6.52 | 115% / 99% |

**用户要求 2 单独就买到了几乎全部收益**：轴 A 的 +2.24 里，+2.14 来自"不丢行"，
只有 +0.10 来自窗口。九个口径上 C 占 A 的 95~115% —— 分工干净到不需要解释。
→ **"截断产生的半句话有害"这个担心被直接否掉**：截断代替丢行在**每一个**口径上都是正的。

一致性检查：|A − (B + C)| = |2.24 − (0.10 + 2.14)| = **0.00** ≤ 0.91 ✅。
⚠️ **但这一项事后看是无效检查**：三条轴都由同三个测量值作差得到，
A ≡ B + C 是代数恒等式，它只能抓抄写错误、抓不了任何实质问题。
**教训：设计"一致性检查"前先确认三个量不是同一批数的线性组合**
（要真做这件事，需要 L0′ 这类独立臂）。

### 5.22.5 顺带落地的三条（都不在预登记判据里，但值得记）

1. **PCM 的 IN-1k 代价在等量数据下消失。** 此前"PCM 在 IN-1k 上是稳定显著负项"
   （L0 21.53 vs `gt_base` 23.27 = **−1.74**）**混着"dense 丢行导致唯一数据少 31%"这一项**。
   L1/L2 与 `gt_base` **数据量相同**（都是 289.4 万行）→ L1 23.77 相对 23.27 是
   **+0.50 = 0.78× 2φ（不可分辨）**。→ 正确表述改成：
   **PCM 在 IN-1k 上的代价主要是数据代价，不是长文本代价；补齐数据后它落回噪声内。**
2. **图像塔坑也缩掉约 2/3。** k-NN bb：L0 相对 `gt_base` 44.73 是 −3.29（11σ），
   L1 43.66 是 **−1.07（3.6× 2φ，仍显著负但只剩 1/3）**；k-NN proj 反而
   **+0.75（2.6× 2φ，显著为正）**。Δ(proj − bb) = +0.37 仍落在 PCM 系签名区间（+0.31）。
   → 「长文本收益是用图像塔质量换的」保留，但**"换掉的量"要从 3.3 点改成 1.1 点**。
3. **`_trim_to_batch_max` 在三臂上都失效**（登记项 #5 得到确认）：per-GPU batch 512、
   L1 有 5.67% 的行 ≥320 → P(整 batch 无触顶行) ≈ e⁻²⁹ ≈ 0，每个 batch 都跑满窗口。
   这正是 320 贵 14~16% 的原因（320/256 = 1.25 倍文本塔计算，实测吞吐比 1.16 倍）。

### 5.22.6 押注复盘

预登记押 **A2 + B2 + C1**，实测 **A1 + B2 + C1** —— 两条中、A 押保守了一档
（押"低于数据量外推"，实测超过）。押注理由写的是"数据项应压倒窗口项"，
**这个方向判对了且被 C/A 的 95.5% 占比强化**，只是幅度估低。
连续第三轮"押注错方向或错档、判据替我判对" → 三分带 + 符号的写法继续兑现。

### 6.3 已否决

**用 sub-batch 估主成分方向替代全 batch SVD** —— 想法合理（实测 GPU 上 sub-64
比 full SVD 快 5.6×），但**PCA 不是瓶颈**。PCM 前向逐件计时（B=512, GPU, no_grad）：

| 部件 | 耗时 | 占比 |
|---|---|---|
| 文本塔-长文（92 token） | 1380.5 ms | 56.1% |
| 图像塔 | 998.2 ms | 40.6% |
| 文本塔-短文（8 token） | 62.4 ms | 2.5% |
| **PCA (k=32)** | **19.5 ms** | **0.8%** |

删掉 PCA 也只快 0.8%。而 sub-64 估出的子空间与全 batch 重建 cos 仅 0.615，
等于换了个降维目标 —— 需重跑整组超参才知好坏。风险换 0.8% 速度不划算。

真正的开销在长文本塔（56%）。`_trim_to_batch_max`（§2.3）已把短分支从 256 token
压到 8 token，这是主要收益来源；再砍就要动 dense caption 本身，那是实验变量而非优化。
